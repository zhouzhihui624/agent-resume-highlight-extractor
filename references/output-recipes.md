## 只输出简历内容

严格遵守用户要求的数量和长度，证据分析在内部完成。

句式：

```text
[实习生可信的有限职责] + [核心机制] + [解决的问题] + [已验证结果或机制可推出的价值]
```

优先使用具体名词和动词，不要堆叠技术名称。长度受限时，保留最能区分该亮点的机制，优先删除泛化价值描述。

实习包装模式下，根据项目机制直接选择有限职责，可使用 `参与建设`、`负责其中 X 环节` 或 `围绕 X 完成实现/评测/接入/验证`，不询问个人归属。证据严格模式下才要求归属动词有个人证据。无论哪种模式，都不能把有限职责扩大成主导完整平台，也不能把待核验的精确数字或生产上线事件写成事实。

## 证据审计

用户只有旧材料或不完整材料时使用：

```markdown
## 现在能安全写什么
[一份保守草稿，或者明确说明当前证据仍不足]

## 当前证据能证明什么
- ...

## 还不能写什么
- ...

## 最关键的确认问题
1. ...
2. ...
3. ...
```

最多询问三个问题。每个编号只问一个决定性事实，不要把技术栈、规模、指标和上线情况塞进同一道隐藏问卷。

## 面试叙事主题

标题名称可以根据主题调整，下面约束的是信息顺序和语义，不是一组必须逐字匹配的章节名。

```markdown
# [主题]

## 先记住这件事
> [一句记忆句：场景与问题] + [可信的有限实习职责] + [不超过三个关键设计] + [结果]

- 具体问题: ...
- 最简单方案为什么不够: ...
- 我的任务与团队边界: ...
- 没有这项机制会怎样: ...

## 整体方法
[默认只使用一张 Mermaid flowchart 展示三个实现步骤、关键判断、主要失败和最终输出。节点先写普通中文，不放源码状态名或未解释缩写。只有并发、等待或严格时序本身是难点时才使用 sequenceDiagram。]

[图后立即用一段自然语言从输入开始，把每一步拿到什么、做什么判断、产生什么结果走一遍。]

## 方法是怎样实现的

### 第一步：[动作短语]
- 为什么需要: ...
- 输入、核心对象和规则: ...
- 数据或状态怎样变化: ...
- 正常路径怎样运行: ...
- 失败后怎样处理: ...
- 用什么证据验证: ...
- 为什么没有采用更简单的方案: ...

### 第二步：[动作短语]
...

### 第三步：[动作短语]
...

## 失败、取舍与边界
- 主要失败场景: [现象、处理和剩余边界]
- 部分失败场景: [现象、处理和剩余边界]
- 核心工程取舍: ...
- 可以说: ...
- 不能说: ...

## 怎样证明它有效
- 正常链路由什么测试、轨迹、报告或制品证明: ...
- 失败链路由什么证据证明: ...
- 已形成能力: ...
- 机制可推出的定性价值: ...
- 非事实式上线用途: ...
- 可继续量化的指标口径: ...
- 为什么不只是一次普通大模型调用: ...

## 快速复习和面试表达
- 简历 Bullet: ...
- [只放用户明确要求的 30 秒、2 分钟、10 分钟或 STAR；所有版本沿同一顺序展开]

## 面试官继续追问
[默认保留 3-5 个由正文自然产生的问题。答案复述或展开正文机制，不得首次引入决定主流程成立的对象、规则、提醒方式、恢复行为或验证条件。]

## 证据附录
- 源码和测试定位: ...
- 完整状态、规则或异常矩阵: ...
- 必要术语和待补充指标: ...
...
```

这套结构提供两条阅读路径：

1. 快速复习：一句记忆句 → 整体图 → 图后讲解 → 简历或短版面试话术；
2. 深入掌握：三个实现步骤 → 失败与取舍 → 验证 → 面试追问 → 证据附录。

整体图与三个实现步骤必须一一对应。默认不要再增加一张重复同一路径的“总时序图”，也不要把完整流程、代码实现和关键设计分成三套章节重复讲。每个步骤都在当前位置完成 `为什么 → 怎样做 → 状态变化 → 失败 → 验证 → 取舍` 的闭环。

正文是面试主线，附录是继续查证或处理低频追问时才展开的知识库。完整术语表、角色全集、状态矩阵、规则全集和源码证据可以进入附录，但理解主流程不可缺少的对象、判断和恢复行为必须放在对应实现步骤，不能等到追问区才第一次解释。

结果、价值和架构名称不能替代实现说明。正文必须先用通俗语言讲清对象、规则、状态和调用顺序，再说明这些实现带来的结果；源码文件、结构体和函数名只作为证据定位放入附录。

实习包装模式下，即使没有个人提交证据，也要从入选机制中确定一个有限职责锚点并完成第一人称主线，不把归属确认问题留给用户。证据严格模式下没有个人锚点时，才把 `我的任务和团队边界` 改成 `项目职责拆分与待确认项`，并以 `项目` 或 `该模块` 为主语。

主线最多使用三个设计锚点、两个主要失败场景和一个核心取舍。一个事实只完整解释一次。简历、不同时间版本、STAR 和高频追问只能压缩、复述或展开这条主线，不得重新组织成另一套架构。

只生成用户要求的讲述版本。10 分钟版本必须提供可直接连续讲述的内容或逐段话术，不能只给时间安排表。没有有意义的测量建议时省略待补充指标。

### 初学者可读性门槛

- 以一个具体失败场景和一句故事主张开场，不要先放术语表或架构名词；
- 在正文前三分之一内讲清有限实习职责；只有证据严格模式且个人贡献未知时才写成项目理解稿；
- 全文反复使用同样的三个设计锚点，帮助读者形成记忆，不要不断创造新的分类；
- 必要术语第一次写成 `中文解释（English Term）`，后续优先使用中文；
- 标题、流程图节点、表格表头和快速复习材料同样先用普通中文，不能只把正文段落润色；
- 一段话只承担一个主要概念。必须连续使用多个术语时，先用一句中文说明它们各自扮演的角色，再补名称；
- 除非解释确实离不开，否则源码标识、结构体和函数名放在证据附录；
- 术语表是查询附录，不是正文入口；只收录理解主线确实需要的词；
- 术语定义必须自洽，在解释 `Host` 前先讲清 `SDK`；
- 图示使用读者熟悉的语言，并在图后立即解释流程；图中的 `持久化` 应先写成“保存完整原文”，`单向变化` 应先写成“删掉的旧内容不会被重新带回来”等实际含义；
- 保留谁做决定、状态怎样变化、中断后保留什么、哪里会失败以及剩余取舍；
- 删除不能推进“问题、个人任务、关键设计、流程、失败、结果”因果链的正文段落，把它们移入附录。

不合适的开场：

> Host injects IO into a Host-neutral SDK contract, then Run/Resume restores runtime-state.

更合适的开场：

> 外层应用负责提供模型、文件和命令行能力；智能体运行底座负责按统一流程推进任务。任务暂停后，系统会读取已经保存的会话记录和运行快照，从原位置继续。源码中把这两个入口称为 `Run` 和 `Resume`。

## 单文档深挖整合

用户明确最终只保留一份主题文档，或者反馈“新版更清晰但丢失了原版细节”时使用。目标不是在主线与深度之间二选一，而是让同一份文档同时支持快速复习和深入追问；核心机制仍在对应流程步骤首次讲清，附录只保存扩展材料。

### 重构前先做细节迁移表

对原文每个已核验知识点作出一次明确处理：

| 处理 | 适用内容 |
| --- | --- |
| 进入主线 | 工程问题、有限职责、三个设计锚点、完整流程、主要失败、核心取舍和结果边界 |
| 移入深挖附录 | 对象关系、规则全集、输入构造、状态与制品、异常矩阵、替代方案、观测成本、指标口径和证据 |
| 删除 | 重复流程、平行分类、错误事实、无关平台介绍、只为显得复杂的术语和源码导览 |

不得用“从多少行缩到多少行”证明重构成功。每项高价值事实必须能够在新文档中找到稳定位置，或者有明确删除理由。

### 使用一个文档的分层结构

```text
第一层：具体问题、一句记忆句、一张整体图、图后讲解、简历与短版话术
第二层：按图展开的三个实现步骤、主要失败、核心取舍、验证和结果边界
第三层：完整对象关系、规则与状态矩阵、低频异常、观测、指标和源码证据
```

正文继续遵守三个设计锚点、两个主要失败和一个核心取舍。第一层让用户能快速复习，第二层承担“具体怎样实现”的主要解释，第三层用于查证和低频追问。用户要求“一个文档讲透”时，附录不受默认 3-5 个深挖点限制，但每个章节必须回答主线产生的自然追问，不能引入第二套分类体系，也不能把第二层本应解释的核心机制推迟到附录。

### 深度完整性检查

根据项目实际证据检查下列问题；不适用的项目可以省略，不能使用通用 Agent 知识补齐：

1. 系统实际处理哪些对象，它们怎样关联？
2. 触发入口收到哪些输入，最终输出和真实副作用是什么？
3. 判断、排序、校验或路由按什么顺序进行，阈值、预算和兜底规则是什么？
4. 上一步输出怎样转换并交给下一模块，而不是只写“然后调用”？
5. 正常路径中数据、状态、草稿、提交或其他制品怎样变化？
6. 哪个时间点真正执行文件修改、工具调用、发布或其他不可逆副作用？
7. 内容错误、运行错误、基础设施错误和用户取消是否有不同终态？
8. 失败后是重试、回滚、降级、恢复还是转人工，恢复时读取哪些状态？
9. 测试、运行轨迹、评测报告或制品怎样证明关键契约成立？
10. 为什么没有采用更简单的纯规则、纯模型、直接重试或人工方案？
11. 如何区分主流程与补救流程的耗时、成本或观测记录？
12. 哪些结果已经验证，哪些只是上线用途或可量化方向？

最终做一次脱稿检查：用户应能先沿主线连续讲，再在面试官追问三层后从附录取出细节，而不是背诵整篇文档。

## 面试深挖包

先构造一条稳定的回答链：

```text
你做了什么
→ 为什么需要它
→ 最简单方案为什么不够
→ 你做了哪三个关键设计
→ 一次任务怎样运行
→ 失败时怎么办
→ 为什么这样取舍
→ 结果和边界是什么
```

再按用户需要生成一种或多种讲述深度：

- **30 秒**：问题、有限实习职责、机制和结果；
- **2 分钟**：沿回答链完整讲一遍，展开一个失败边界；
- **10 分钟**：沿同一回答链展开状态、失败窗口、替代方案和剩余限制，使用自然过渡形成连续讲述；
- **STAR**：60-90 秒故事，其中行动部分必须包含个人技术工作。

不同版本必须复用相同的个人任务、三个设计锚点和结果边界。然后把以下类别放进追问附录：

- 为什么不是一次普通大模型接口调用？
- 这段机制位于完整生命周期的哪个位置？
- 核心数据流和状态流是什么？
- 哪些状态只在内存，哪些可以跨请求或跨进程保存？
- 如何测试或评估？
- 最大的失败模式是什么？
- 正常路径、取消路径和崩溃恢复有什么不同？
- 是否存在并发、重复请求、幂等或部分副作用问题？
- 为什么选择这个方案而不是更简单的替代方案？
- 为什么把你的职责收敛到这一环，而不是整个平台？
- 哪部分属于团队平台、宿主或上下游系统？
- 结果如何衡量，哪些指标还没有？

`Action` 部分必须包含职责锚点内的技术决策和具体动作，不能只有协调类动词。没有量化数据时，`Result` 除了已验证能力，还应同时给出机制能够直接推出的定性价值和非事实式上线用途，例如 `降低回归风险` 与 `支撑模型升级前验收`。

## JD 定制

先把岗位要求映射到证据：

| JD 要求 | 对应证据 | 强度 | 简历角度 |
| --- | --- | --- | --- |

然后只写最强的定制简历内容。把明显缺少证据的岗位要求单独列出，不要用相邻技术强行代替。

不同岗位的侧重点：

- **AI Agent 工程师**：编排、工具、上下文、记忆、评测、安全和链路追踪；
- **AI 应用工程师**：用户流程、业务接入、可靠性、评测和部署；
- **代码智能体工程师**：仓库理解、问题到补丁闭环、沙箱与测试、软件工程任务评测；
- **后端或 AI 基础设施**：运行边界、模型提供方抽象、状态、恢复、权限、成本和可观测性。

## 保存文档包

落盘前先把现有文件分成六类：

| 文档角色 | 是否计入正式亮点 | 推荐处理 |
| --- | --- | --- |
| 正式亮点 | 是 | 使用完整面试叙事与实现结构 |
| 总览或索引 | 否 | 保存项目定位、阅读顺序和简历汇总 |
| 关系说明 | 否 | 解释仓库、平台或评测层级之间的边界 |
| 独立项目 | 单独统计 | 形成另一段项目经历，不塞入当前项目 |
| 候选储备 | 否 | 放入候选目录，说明为何暂不推荐 |
| 历史材料 | 否 | 只作迁移和事实核对来源 |

不要因为文件位于同一目录或带有编号，就把它们都算成正式亮点或强迫使用同一模板。完成角色分类后，再使用精简目录：

```text
resume-highlight-docs/
  README.md
  00-summary-and-resume.md
  01-<strong-theme>.md
  02-<strong-theme>.md
  ...
```

`README.md` 保存索引、文档角色和阅读顺序。总览文档保存最终简历内容、项目定位、入选理由、实习职责锚点、结果包装级别和真正需要核验的精确指标。每个正式主题文档遵循面试叙事主题模板；关系说明、独立项目和候选材料使用各自最自然的结构。

重构现有文档包时，合并薄弱重复主题，推荐阅读路径只保留入选主题。不要仅因为旧文件已经存在就继续保留。用户没有明确授权物理删除时，不要删除文件；按用户要求保留原位或移动到候选、历史等可恢复目录。

多个子 Agent 并行起草时，为每个子 Agent 分配互不重叠的文件。主 Agent 最后统一检查术语中文化、设计锚点名称、职责边界、事实快照、相对链接和证据路径；不能把多份局部草稿直接拼接后交付。

## 个人贡献级别

按模式选择归属级别：

1. `主导 / 独立负责完整系统`：仅在用户明确提供所有权证据时使用，实习包装模式不得推导；
2. `负责其中 X 模块 / 设计并实现其中 X 环节`：实习包装模式可在对象明确、动作具体、工作量可信时使用；
3. `参与建设 / 参与设计`：实习包装模式的常用级别，必须紧跟具体模块和技术动作；
4. `协助实现 / 参与联调 / 完成调研与沉淀`：适合支持性、接入或验证工作。

实习包装模式允许根据仓库中已确认的项目能力推导第 2-4 级有限职责，但不得仅把 `主导` 换成 `参与` 后照搬平台级范围。证据严格模式仍按用户陈述、任务、提交或其他归属证据选择最高级别。

## 实习生适配门槛

对学生和实习生，要单独检查工作范围是否可信。目标不是证明代码归属，而是把项目能力切成候选人能连续讲透、工作量合理的职责单元。把 `主导` 换成 `参与`，不能让过大的表述自动变得可信。

每个入选主题都应回答：

1. 可以把该能力收敛成哪个有限模块、链路、实验、接入或验证任务？
2. 该职责锚点对应哪些具体技术动作？
3. 哪些输入由上游团队或平台提供？
4. 哪些下游运行、服务、产品或发布职责不属于用户？
5. 所述工作量在实习周期内是否可信？
6. 用户能否基于项目机制解释一个失败、一个取舍和一个验证结果？

回答不了第 1、2 项时，说明主题过大或机制太薄，应继续拆分或淘汰；不要把它原样包装成平台级第一人称经历。

推荐结构：

```text
[团队项目背景] + [有限实习职责] + [具体技术动作] + [模块级结果或定性价值] + [明确平台边界]
```

不能为了适合实习生而降低技术深度。应保留机制深度，同时把个人范围从 `完整平台` 收敛到具体质量门禁、评测实验、反馈闭环、协议适配、接入或验证职责。

## 结果表述

先判断结果属于哪一层：

| 层级 | 可以怎样写 | 例子 |
| --- | --- | --- |
| 已验证结果 | 陈述已有能力、观测指标和实际接入或上线状态 | `覆盖关键恢复路径`、`接入发布前检查流程` |
| 机制可推出的价值 | 直接写合理的定性作用，并补充非事实式上线用途 | `降低回归风险`、`提升问题复现与定位效率`；`支撑上线前质量验收` |
| 待核验的精确结果 | 只在附录给出建议口径，不写成已发生事实 | 成功率、耗时降幅、用户量、成本金额、线上流量 |

有真实指标时说明指标及统计口径；没有精确指标时优先使用：

- 支持 / 打通 / 建立
- 沉淀为可复现、可回归的流程
- 形成可暂停、可恢复、可审计的执行语义
- 降低手工复现或排查成本
- 为后续模型对比或扩展提供统一基础

用户允许包装指标或上线效果时，从机制中选择最贴近岗位的定性价值，并补充 1-3 个可量化口径供面试准备。避免使用没有证据的 `显著提升`、`生产级`、`高并发`、`SOTA`、`完全自动化`、虚构百分比和“已在生产上线”。

## 转换示例

证据：项目使用按剧本响应的模型替身和内存输入输出环境，驱动真实 Agent 的 `Run/Resume` 路径，并断言工具调用、文件、事件和会话状态。

实习包装模式直接把它收敛成测试环节，而不是声称负责完整智能体平台：

> 参与建设智能体场景化端到端测试，通过剧本模型和内存环境驱动真实任务启动与恢复流程，沉淀工具调用、中断恢复的可复现回归场景，降低核心链路改动的回归风险。

这句话中的 `参与建设测试环节` 是有限职责包装，`降低回归风险` 是机制能够直接推出的定性价值。若要写 `回归缺陷下降 30%` 或 `已作为生产发布门禁上线`，仍需对应数据或上线材料；没有时把缺陷数量、场景覆盖率、回归耗时和发布拦截数列为可量化口径。

证据严格模式下，如果个人锚点未知，才改用 `项目通过...` 的项目机制表述。
