## 只输出简历内容

严格遵守用户要求的数量和长度，证据分析在内部完成。

句式：

```text
[符合个人范围的动词] + [机制或贡献] + [解决的问题] + [有证据的结果]
```

优先使用具体名词和动词，不要堆叠技术名称。长度受限时，保留最能区分该亮点的机制，优先删除泛化价值描述。

严格格式不能覆盖事实安全。个人贡献没有证据时，不使用 `参与`、`负责`、`设计并实现` 等动词；只能输出项目能力理解稿、在要求允许时标记待确认，或先询问一个决定性问题。

## 证据审计

用户只有旧材料或不完整材料时使用：

```markdown
## 现在能安全写什么
[一份保守草稿，或者明确说明当前证据仍不足]

## 当前证据能证明什么
- ...

## 还不能写什么
- ...

## 最关键的确认问题
1. ...
2. ...
3. ...
```

最多询问三个问题。每个编号只问一个决定性事实，不要把技术栈、规模、指标和上线情况塞进同一道隐藏问卷。

## 面试叙事主题

```markdown
# [主题]

## 一句话讲清
> [场景与问题] + [有证据的个人任务] + [不超过三个关键设计] + [可验证结果]

## 这项工作解决了什么问题
- 具体场景: ...
- 原来的问题: ...
- 最简单方案为什么不够: ...
- 没有这项机制会怎样: ...

## 我的任务和团队边界
- 团队项目背景: ...
- 我的个人锚点: ...
- 上游由谁提供: ...
- 下游和平台职责不属于我: ...

## 先记住三个设计锚点
1. [动作短语]: ...
2. [动作短语]: ...
3. [动作短语]: ...

## 跟着一次任务走完整主线
1. [触发和输入]
2. [关键判断]
3. [状态或制品变化]
4. [失败或反馈]
5. [输出和终态]

## 三个关键设计为什么这样做
### [设计锚点一]
[决策、机制、简单替代方案为什么不够]

### [设计锚点二]
...

### [设计锚点三]
...

## 失败时怎么办
- 主要失败场景: [现象、处理和剩余边界]
- 部分失败场景: [现象、处理和剩余边界]

## 结果、含金量和事实边界
- 已形成能力: ...
- 为什么不只是一次普通大模型调用: ...
- 可以说: ...
- 不能说: ...

## 面试怎么连续讲
[只放用户明确要求的 30 秒、2 分钟、10 分钟或 STAR 版本；所有版本沿同一顺序展开]

## 追问附录
### 必要术语
...

### 角色、状态或制品补充
...

### 高频追问
...

### 证据路径与待补充指标
...
```

正文是面试主线，附录是继续追问时才展开的知识库。完整术语表、所有状态、规则全集和源码证据不得默认进入正文。追问附录默认只保留 3-5 个最能解释主线的深挖点。

没有个人锚点时，把 `我的任务和团队边界` 改成 `项目职责拆分与待确认项`，整篇标记为项目机制理解稿，不生成第一人称 STAR。若用户明确要求项目机制讲法，讲法以 `项目` 或 `该模块` 为主语；个人贡献免责声明放在讲法之外，不要让候选人把“现有材料无法证明”当作面试开场。

主线最多使用三个设计锚点、两个主要失败场景和一个核心取舍。一个事实只完整解释一次。简历、不同时间版本和 STAR 只能压缩或展开这条主线，不得重新组织成另一套架构。

只生成用户要求的讲述版本。10 分钟版本必须提供可直接连续讲述的内容或逐段话术，不能只给时间安排表。没有有意义的测量建议时省略待补充指标。

### 初学者可读性门槛

- 以一个具体失败场景和一句故事主张开场，不要先放术语表或架构名词；
- 在正文前三分之一内讲清用户个人任务；个人贡献未知时明确写成项目理解稿；
- 全文反复使用同样的三个设计锚点，帮助读者形成记忆，不要不断创造新的分类；
- 必要术语第一次写成 `中文解释（English Term）`，后续优先使用中文；
- 除非解释确实离不开，否则源码标识、结构体和函数名放在证据附录；
- 术语表是查询附录，不是正文入口；只收录理解主线确实需要的词；
- 术语定义必须自洽，在解释 `Host` 前先讲清 `SDK`；
- 图示使用读者熟悉的语言，并在图后立即解释流程；
- 保留谁做决定、状态怎样变化、中断后保留什么、哪里会失败以及剩余取舍；
- 删除不能推进“问题、个人任务、关键设计、流程、失败、结果”因果链的正文段落，把它们移入附录。

不合适的开场：

> Host injects IO into a Host-neutral SDK contract, then Run/Resume restores runtime-state.

更合适的开场：

> 外层应用负责提供模型、文件和命令行能力；智能体运行底座负责按统一流程推进任务。任务暂停后，系统会读取已经保存的会话记录和运行快照，从原位置继续。源码中把这两个入口称为 `Run` 和 `Resume`。

## 面试深挖包

先构造一条稳定的回答链：

```text
你做了什么
→ 为什么需要它
→ 最简单方案为什么不够
→ 你做了哪三个关键设计
→ 一次任务怎样运行
→ 失败时怎么办
→ 为什么这样取舍
→ 结果和边界是什么
```

再按用户需要生成一种或多种讲述深度：

- **30 秒**：问题、有限个人贡献、机制和结果；
- **2 分钟**：沿回答链完整讲一遍，展开一个失败边界；
- **10 分钟**：沿同一回答链展开状态、失败窗口、替代方案和剩余限制，使用自然过渡形成连续讲述；
- **STAR**：60-90 秒故事，其中行动部分必须包含个人技术工作。

不同版本必须复用相同的个人任务、三个设计锚点和结果边界。然后把以下类别放进追问附录：

- 为什么不是一次普通大模型接口调用？
- 这段机制位于完整生命周期的哪个位置？
- 核心数据流和状态流是什么？
- 哪些状态只在内存，哪些可以跨请求或跨进程保存？
- 如何测试或评估？
- 最大的失败模式是什么？
- 正常路径、取消路径和崩溃恢复有什么不同？
- 是否存在并发、重复请求、幂等或部分副作用问题？
- 为什么选择这个方案而不是更简单的替代方案？
- 哪部分是你本人负责的？
- 哪部分属于团队平台、宿主或上下游系统？
- 结果如何衡量，哪些指标还没有？

`Action` 部分必须包含技术决策和实际工作，不能只有协调类动词。没有指标时，`Result` 应写成已验证能力，例如可复现回归、可恢复审批或一致回放。

## JD 定制

先把岗位要求映射到证据：

| JD 要求 | 对应证据 | 强度 | 简历角度 |
| --- | --- | --- | --- |

然后只写最强的定制简历内容。把明显缺少证据的岗位要求单独列出，不要用相邻技术强行代替。

不同岗位的侧重点：

- **AI Agent 工程师**：编排、工具、上下文、记忆、评测、安全和链路追踪；
- **AI 应用工程师**：用户流程、业务接入、可靠性、评测和部署；
- **代码智能体工程师**：仓库理解、问题到补丁闭环、沙箱与测试、软件工程任务评测；
- **后端或 AI 基础设施**：运行边界、模型提供方抽象、状态、恢复、权限、成本和可观测性。

## 保存文档包

使用精简目录：

```text
resume-highlight-docs/
  README.md
  00-summary-and-resume.md
  01-<strong-theme>.md
  02-<strong-theme>.md
  ...
```

`README.md` 保存索引和阅读顺序。总览文档保存最终简历内容、项目定位、入选理由、个人锚点状态和待确认项。每个主题文档遵循面试叙事主题模板，正文只保留一条主线，追问材料进入附录。

重构现有文档包时，合并薄弱重复主题，推荐阅读路径只保留入选主题。不要仅因为旧文件已经存在就继续保留。用户没有明确授权物理删除时，把淘汰文档移动到可恢复备份，而不是删除。

## 个人贡献级别

只有个人贡献证据存在时，才选择它能够支持的最高级别：

1. `主导 / 独立负责`：有明确子系统或工作流所有权；
2. `负责 X 模块 / 设计并实现 X`：有具体提交、MR/PR、任务或用户确认；
3. `参与建设 / 参与设计`：有用户确认、任务记录或其他证据表明本人参与，但范围有限或与他人共享；
4. `协助实现 / 参与联调 / 完成调研与沉淀`：支持性贡献。

仓库存在某项能力不构成第 3 级证据。不能仅根据 Git 作者信息推断产品所有权，也不能把 `参与` 当作个人证据缺失时的默认安全动词。

## 实习生适配门槛

对学生和实习生，要单独检查工作范围是否可信。把 `主导` 换成 `参与`，不能让过大的表述自动变得可信。

每个入选主题都应回答：

1. 用户具体参与了哪个有限模块、链路、实验、接入或验证任务？
2. 用户本人完成了哪些技术动作？
3. 哪些输入由上游团队或平台提供？
4. 哪些下游运行、服务、产品或发布职责不属于用户？
5. 所述工作量在实习周期内是否可信？
6. 用户能否根据个人经历解释一个失败、一个取舍和一个验证结果？

回答不了第 1、2 项时，该主题只能作为架构理解或项目背景，不能生成第一人称简历和 STAR。

推荐结构：

```text
[团队项目背景] + [有限个人模块] + [个人技术动作] + [模块级结果] + [明确平台边界]
```

不能为了适合实习生而降低技术深度。应保留机制深度，同时把个人范围从 `完整平台` 收敛到具体质量门禁、评测实验、反馈闭环、协议适配、接入或验证职责。

## 结果表述

有真实指标时说明指标及统计口径；没有指标时优先使用：

- 支持 / 打通 / 建立
- 沉淀为可复现、可回归的流程
- 形成可暂停、可恢复、可审计的执行语义
- 降低手工复现或排查成本
- 为后续模型对比或扩展提供统一基础

避免使用 `显著提升`、`生产级`、`高并发`、`SOTA`、`完全自动化` 和虚构百分比。

## 转换示例

证据：项目使用按剧本响应的模型替身和内存输入输出环境，驱动真实 Agent 的 `Run/Resume` 路径，并断言工具调用、文件、事件和会话状态。

仅凭上述仓库证据，可以先生成项目机制理解稿：

> 项目通过剧本模型和内存环境驱动真实任务启动与恢复路径，对工具调用、事件和会话状态进行可复现回归。

只有用户确认本人参与该测试模块后，才能改成个人简历表述：

> 参与建设智能体场景化端到端测试体系，通过按剧本返回的模型替身与内存环境驱动真实任务启动和恢复流程，沉淀工具调用与中断恢复的可复现回归场景。

两种写法共享同一机制，但只有第二种包含个人归属。准确源码术语仍可在后续证据部分出现。
